# 착수 회의용 문서 검토 예제

**직접 작성한 합성 자료이며 사람이 검토·확정한 정답셋이 아니다.** 현재 추천 주제의 난이도와 평가 기준을 이야기하기 위한 예제다. 실제 제품의 품질을 평가하거나 파인튜닝 성과를 주장하는 데 사용하지 않는다.

기계가 읽을 입력·예상 출력: [starter-review-fixture.json](./starter-review-fixture.json)

## 입력 A: 요구사항 정의서 v1

| ID | 요구사항 |
| --- | --- |
| REQ-01 | 동일 계정으로 비밀번호를 연속 5회 틀리면 계정을 30분 동안 잠근다. |
| REQ-02 | 계정 잠금 기간에는 올바른 비밀번호를 입력해도 로그인을 거절한다. |
| REQ-03 | 회원 비활성화는 관리자에게만 허용하고 일반 회원의 요청은 거절한다. |
| REQ-04 | 비밀번호 재설정 링크는 발급 후 15분이 지나면 사용할 수 없다. |
| REQ-05 | 문의 제목은 1자 이상 100자 이하만 허용하고, 범위를 벗어난 입력은 저장하지 않는다. |
| REQ-06 | 회원 목록 조회는 빠르게 응답해야 한다. |

## 입력 B: 테스트 명세서 v1

이 예제에서는 다음 7개 항목이 테스트 명세 전체라고 가정한다. 다른 버전이나 누락된 페이지는 없다.

| ID | 시험 절차 | 기대 결과 |
| --- | --- | --- |
| TC-01 | 활성 계정으로 잘못된 비밀번호를 연속 5회 입력한다. | 다섯 번째 실패 후 계정 잠금 상태가 된다. |
| TC-02 | 계정이 잠긴 지 10분 후 올바른 비밀번호로 로그인한다. | 로그인에 성공한다. |
| TC-03 | 관리자가 활성 회원의 비활성화를 요청한다. | 요청을 허용하고 해당 회원을 비활성 상태로 변경한다. |
| TC-04 | 일반 회원이 다른 회원의 비활성화를 요청한다. | 요청을 거절하고 대상 회원의 상태를 유지한다. |
| TC-05 | 제목 길이를 1자, 100자로 각각 설정해 문의를 저장한다. | 두 경우 모두 저장된다. |
| TC-06 | 제목 길이를 0자, 101자로 각각 설정해 문의를 저장한다. | 두 경우 모두 유효성 오류를 표시하고 저장하지 않는다. |
| TC-07 | 회원 목록을 조회한다. | 빠르게 결과가 표시된다. |

## 예상 검토 결과 초안

| 요구사항 | 판정 | 연결 근거 | 판정 이유 |
| --- | --- | --- | --- |
| REQ-01 | partial | TC-01 | 5회 실패 후 잠금은 확인하지만 30분 잠금 유지·해제 조건의 검증은 기재되지 않았다. |
| REQ-02 | conflict | TC-02 | 요구사항은 잠금 중 로그인 거절을 요구하지만 TC-02는 잠금 후 10분에 로그인 성공을 기대한다. |
| REQ-03 | covered | TC-03, TC-04 | 관리자 허용과 일반 회원 거절을 모두 명시한다. |
| REQ-04 | missing | 전체 명세 검토 | 전체 테스트 명세 TC-01~TC-07에 재설정 링크 만료를 확인하는 항목이 없다. |
| REQ-05 | covered | TC-05, TC-06 | 허용 경계 1·100자와 거절 경계 0·101자를 모두 확인한다. |
| REQ-06 | needs_review | TC-07 | 요구사항과 테스트 모두 '빠르게'의 시간 기준과 측정 조건이 없어 합격 기준을 정할 수 없다. |

REQ-01의 제안은 잠금 유지 시간에 대한 테스트 추가, REQ-02는 잘못된 기대 결과 수정, REQ-04는 링크 만료 테스트 추가다. REQ-06은 임의로 시간 기준을 만들어 넣지 않고 담당자에게 합격 기준을 요청해야 한다.

## 이 예제로 먼저 합의할 것

- **검토 단위:** 요구사항 하나에 테스트 여러 개를 연결할 수 있다.
- **판정 대상:** 문서상 시험 범위를 판단한다. 실제 코드가 구현되었는지, 테스트가 실행·통과했는지는 별도 증거가 필요하다.
- **부분 충족과 미기재:** 일부 조건을 다루면 partial, 전체 명세에 대응 항목이 없으면 missing이다.
- **근거 범위:** 검색 결과 몇 개에서 못 찾았다는 이유만으로 missing을 반환하지 않는다.
- **충돌:** 연결된 테스트에 명시적 모순이 있으면 다른 정상 테스트가 있다고 단순 covered로 처리하지 않는다.
- **모호함:** 합격 기준·문서 버전·입력 범위가 불명확하면 needs_review로 넘긴다.
- **수정 권한:** 자동으로 원본을 덮어쓰지 않고 수정 제안과 담당자 채택 여부를 남긴다.

## 이후 확장

팀원이 사례를 독립적으로 판정한 뒤 의견이 갈리는 항목부터 기준을 보완한다. 새로운 요구사항·문서 유형·표현으로 개발용 사례를 확장하고, 실제 업무 자료로 타당성을 확인한다. 현재 예제와 유사한 문장을 조금 바꾼 것만으로 최종 평가셋을 구성하지 않는다.
