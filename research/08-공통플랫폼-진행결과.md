| 영역 | 현재 구현 |
| --- | --- |
| 업무 교체 | 팩별 이름·입력·판정 문구·프롬프트·예제 분리, 두 주제 실행 확인 |
| 에이전트 흐름 | 기준 추출 → 근거 검색 → 검토 → 독립 검증 → 사람 검토 |
| 근거 확인 | 문서 버전·청크·원문, 인용 검증 실패 시 사람 확인으로 전환 |
| 검토 화면 | 문서 입력·파일 불러오기·결과·근거 열기·제안 수정·채택/반려 |
| 기록 | SQLite 저장, 실행 다시 보기, 동시 수정 충돌 감지, 변경 이력 |

| 모델 연결 준비 | vLLM 호환 API 연결부, 단계별 모델·LoRA 별칭 설정 |
| 학습 준비 | 데이터 규격·중복/분할 누출 검사·검수된 train 자료의 SFT 내보내기 |
| 평가 준비 | 문서 해시로 고정한 평가 입력, 판정별 지표·혼동 행렬·검색 문맥 회수율 |
| 협업 준비 | API/JSON 계약, 이슈·PR 양식, 코드 규칙, CI 설정, 역할별 백로그 |

## 주제가 정해지면 채울 부분

1. **대상 업무와 사용자의 판단 기준**을 확정합니다. 어떤 문서를 받아 어떤 결과를 업무에 쓰는지 한 문장으로 정합니다.
2. 해당 주제의 packs 폴더에서 입력 예제·기준·프롬프트·화면 문구를 교체합니다.
3. 이용 가능한 실데이터와 정답을 확보하고, 학습·개발·평가 세트를 문서/사례 그룹 단위로 분리합니다.
4. RunPod 모델 서버를 연결하고, 검토 단계처럼 역할이 명확한 태스크 하나부터 sLLM 파인튜닝을 진행합니다.
5. 같은 평가셋으로 학습 전후 품질·오류·시간·비용을 비교합니다.

문서 기반 검토 업무는 위 구조를 재사용할 수 있습니다. 음성·OCR·외부 시스템 조작 등 입력이나 실행 방식이 달라지는 주제는 공통 구조에 추가 연결부가 필요합니다.

## 현재 완성도 해석

**실행 가능한 공통 기반과 개발 도구가 준비된 상태**입니다. 고정 응답을 재생하는 데모이며 실제 모델 추론, 파인튜닝, 현업 품질 검증은 아직 하지 않았습니다. 모델 API·GPU 비용을 지출하지 않았습니다.

자동 테스트 35개, 코드 검사, 두 주제의 브라우저 흐름을 확인했습니다. 2026-09-27 GitHub 업로드 후 원격 CI도 통과했습니다. Docker는 설정만 포함했습니다. 팀 전체 진행률이나 최종 프로젝트 완성률을 임의의 숫자로 표현하지 않습니다.
