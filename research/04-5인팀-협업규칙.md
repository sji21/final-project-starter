# 5인팀 협업 규칙 초안

조건: 약 6주, 5명, 사용자 PM, RunPod 사용 예정. 실제 팀원 역량과 수업 일정에 맞춰 착수 회의에서 확정한다.

## 1. 역할과 책임

| 역할 | 주 책임 | 주요 산출물 | 대체·검토 역할 |
| --- | --- | --- | --- |
| PM — 사용자 | 범위·우선순위·사용자 시나리오·완료 기준·통합 일정 | 백로그, 평가 기준, 데모 시나리오, 발표의 문제·가치 부분 | 기술 리드와 범위 결정, 데이터 담당과 정답 검토 |
| 백엔드·기술 리드 | API·DB·인증·작업 상태·배포·통합 | 실행 환경, API 계약, 장애 처리, 배포 절차 | 에이전트 담당이 API 검토·대체 |
| 에이전트·RAG | 검색·워크플로·도구·근거 연결 | 에이전트 계약, 검색 평가, 실행 추적 | 백엔드 담당과 인터페이스 교차 검토 |
| 데이터·sLLM | 데이터 품질·분할·학습·모델 평가·서빙 연결 | 데이터 버전, 어댑터, 학습 기록, 비교 결과 | 에이전트 담당이 추론·평가 대체 |
| 프런트엔드·UX | 입력·근거 표시·수정·승인·오류 화면 | 실제 API가 연결된 사용자 흐름 | PM이 시나리오 검토, 백엔드 담당이 계약 검토 |

역할은 독점 구역이 아니다. 각 기능에는 개발 담당 1명과 검토자 1명을 지정한다. PM은 모든 PR의 필수 승인자가 되지 않고, 사용자 흐름이나 범위가 바뀌는 변경을 확인한다. 발표 자료와 검증 증거도 각 담당자가 자신의 부분을 작성한다.

## 2. 매일·매주 운영

- 매일 10분: 완료한 산출물, 오늘 합칠 변경, 막힌 점만 공유한다.
- 막힌 문제를 30~60분 확인해도 다음 시도가 안 보이면 재현 방법과 로그를 공유한다. 하루 종일 혼자 붙들지 않는다.
- 리뷰 시간은 하루 두 번 고정한다. 예: 11:30, 16:30. 시간은 팀 일정에 맞춰 변경한다.
- 한 사람의 주 작업은 1개로 제한한다. 병렬로 여러 기능을 시작하기보다 완료 후 다음 작업을 가져간다.
- 작업 카드는 보통 0.5~2일 크기로 나눈다. 3일 이상이면 중간 산출물을 별도 카드로 나눈다.
- 매주 실제로 연결된 화면과 결과물로 데모한다. 계획 슬라이드나 모의 응답만으로 완료 처리하지 않는다.
- 금요일 데모 후 20분 동안 다음 주 범위와 가장 큰 위험 3개를 정한다.

이 시간·횟수는 운영 제안이다. 출석·학습 일정과 충돌하면 팀 합의로 바꾸되 리뷰와 통합 시간을 없애지는 않는다.

## 3. Git·PR

1. main은 실행 가능한 상태를 유지한다.
2. 이슈 하나에 짧은 기능 브랜치를 만든다. 개인 이름의 장기 브랜치는 기본으로 쓰지 않는다.
3. 첫 동작이 나오면 Draft PR을 열어 인터페이스를 일찍 공유한다.
4. PR 하나는 한 가지 목적을 가진다. 1~2일 안에 검토·합칠 수 있는 크기를 우선한다.
5. 관련 담당자 1명의 사람 리뷰와 필요한 자동 검사를 통과하면 합친다.
6. 짧은 기능 브랜치는 squash merge를 기본으로 정하고 합친 후 정리한다.
7. API·공통 타입·DB 변경은 사용 측 담당자를 리뷰에 포함한다.
8. main에 직접 push하지 않는 규칙과 필수 검사를 저장소 설정으로 적용한다. 저장소 플랜·권한상 설정이 가능한지는 생성 후 확인한다.

이 방식은 GitHub Flow의 짧은 브랜치·PR 검토·검사 후 병합을 바탕으로 단순화했다. [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow), [병합 방식과 squash 참고](https://docs.github.com/en/pull-requests/reference/pull-request-merges).

### PR에 반드시 남길 것

해결한 문제, 사용자에게 보이는 변화, 관련 이슈, 확인한 정상·실패 사례, 화면 변경이면 캡처, API/데이터/모델 호환성 영향이다. “AI가 작성함”, “코드가 실행됨”만으로 검증 설명을 대신하지 않는다.

## 4. 통합 충돌 줄이기

- 2일차까지 문서 ID, 작업 ID, 결과 상태, 오류 형식, 에이전트 입출력 스키마를 정한다.
- 모의 응답은 팀 공통 예시 파일을 사용한다. 화면과 백엔드가 각자 다른 JSON을 만들지 않는다.
- API 변경은 요청·응답 예시와 사용하는 화면을 함께 확인한다. 파괴적 변경은 같은 PR 또는 연결된 PR로 반영한다.
- 공통 파일을 동시에 크게 수정할 때는 이슈에 먼저 알린다. 모든 변경에 회의를 추가하지는 않는다.
- 새 기능은 정상 경로 하나부터 main에 연결하고 예외·고도화를 이어 붙인다.
- 데이터베이스 변경은 마이그레이션 파일로 공유한다. 개인 DB 수동 수정만으로 완료 처리하지 않는다.
- 로컬 실행법은 새 팀원이 문서대로 실행할 수 있는지 첫 주에 교차 확인한다.

## 5. 에이전트·모델 계약

모든 역할은 입력, 출력 스키마, 사용할 도구, 상태, 실패 처리, 근거 형식을 문서화한다.

- 상태는 성공, 추가 입력 필요, 사람 검토 필요, 오류를 구분한다.
- 근거는 문서·버전·페이지/문단으로 연결한다.
- 모델이 만든 수치·ID·SQL·도구 인수는 해당 유형의 코드 검사로 확인한다.
- 타임아웃·재시도·최대 토큰을 명시한다. 초기값으로 일시적인 읽기/API 오류 재시도 최대 2회, 의미 수정 루프 최대 1회를 제안한다.
- 외부 쓰기 작업은 재시도 전에 멱등성을 확보하고 사용자 확인 상태를 검사한다.
- 실패 시 임의의 성공 결과를 만들지 않는다. 화면에 다시 시도·자료 보완·사람 확인 중 가능한 행동을 보여준다.
- sLLM 호출이 실제 기능에 연결되었는지 요청 로그의 모델·어댑터 버전으로 확인한다.

숫자 제한은 초기값이다. 관측된 지연·비용과 실패 원인에 맞춰 조정한다.

## 6. 데이터·학습·평가 협업

| 대상 | 운영 규칙 |
| --- | --- |
| 원천 데이터 | 출처·이용 조건·수집일·전처리 버전을 기록 |
| 정답 정의 | PM과 데이터 담당이 합의하고 모호한 사례는 결정 기록에 남김 |
| 데이터 버전 | 데이터 담당이 대표 버전 관리. 대용량 자료는 별도 저장소에 두고 manifest·hash를 Git에 저장 |
| 분할 | 학습·검증·최종 평가를 고정하고 중복 문서·유사 사례 누출 검사 |
| 실험 | 코드·모델·데이터·프롬프트·환경·비용·결과를 한 기록에 연결 |
| 비교 | 같은 조건과 같은 지표 정의로 기준 모델과 개선 모델을 비교 |
| 실패 사례 | 정답을 바꿔 점수를 맞추지 않고 오류 유형과 수정 근거 기록 |
| 최종 평가 | 개발 중 계속 들여다보지 않는 평가셋을 두고 공개 시점·실행 버전 기록 |

학습 담당만 평가를 이해하는 상태를 피한다. 다른 팀원 한 명이 고정 평가를 실행하고 결과를 읽을 수 있어야 한다.

## 7. GPU·서버·비용

- GPU 예약표에는 담당자, 시작·예상 종료, 실험 ID, GPU/모델, 결과 경로를 적는다.
- 학습 시작 전에 짧은 실행으로 저장 경로와 재개 가능성을 확인한다.
- 작업 종료 시 체크포인트·로그를 지속 저장소에 저장하고 자원 상태를 확인한다.
- 하루 사용 비용을 기록하고 주간 예산을 넘기기 전 팀에 공유한다.
- 비밀키는 개인 환경변수나 지정 비밀 저장소로 관리하고 저장소·화면 캡처·학습 데이터에 넣지 않는다.
- 발표 전날 새 환경을 처음 만들지 않는다. 동일 이미지·모델로 cold start와 정상 요청을 미리 확인한다.

RunPod의 중지·종료·볼륨 보존 차이는 [공식 Pod 관리 문서](https://docs.runpod.io/pods/manage-pods)를 따른다. 정확한 가격과 자원 생성 권한은 예산 확정 시 정한다.

## 8. 자동 검사와 완료 정의

PR마다 빠르게 실행할 검사는 형식 검사, 변경한 핵심 규칙·스키마, 모의 모델을 사용한 API·에이전트 계약 검사다. 외부 모델을 실제 호출하는 유료 전체 평가는 매 PR에 무조건 돌리지 않고, 모델·프롬프트·데이터 변경 시 정해진 예산 안에서 수행한다.

업무 카드는 다음을 충족하면 완료한다.

- 요구한 입력과 기대 출력이 구현됨.
- 실제 연결 또는 단계에 맞는 계약 검증을 통과함.
- 대표 실패 사례가 처리됨.
- 필요한 로그·문서·공통 예시가 갱신됨.
- 담당자가 재현 방법과 결과를 PR에 남김.
- 검토자가 확인하고 main에 합침.

모의 데이터만 연결된 기능은 “계약 구현 완료”로 기록할 수 있지만 “실서비스 통합 완료”와 구분한다. 수집된 테스트 수, 실행한 테스트 수, 통과한 테스트 수를 구분한다.

## 9. 문서 최소 세트

처음부터 방대한 문서 체계를 만들지 않는다. 아래 7가지만 살아 있는 문서로 관리한다.

1. README: 목적, 실행법, 현재 가능한 기능.
2. 범위·주간 계획: MVP, 제외 범위, 다음 데모.
3. 인터페이스 계약: API, 상태, 에이전트 입출력.
4. 데이터 기록: 출처, 정제, 버전, 분할.
5. 실험·평가 기록: 조건, 결과, 실패.
6. 결정 기록: 선택지, 선택 이유, 재검토 조건.
7. 배포·복구: 이미지, 환경, 모델, 정상 확인, 장애 대응.

README와 실제 코드가 다르면 사용자가 잘못 기대하는 부분부터 수정한다. “구현 예정 / 구현됨 / 실행 확인 / 평가 완료” 상태를 명시한다. [HelixOps의 공개 문서·코드 비교](./01-HelixOps-우선분석.md)와 [Answervice의 실행 증거 관리](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN29-FINAL-3TEAM/blob/main/src/ai/training/README.md)에서 도출한 규칙이다.

## 10. PM의 주간 확인 5가지

1. 이번 주 결과가 사용자의 업무 한 단계를 실제로 끝내는가.
2. 각 기능의 담당자·검토자와 다음 통합 시점이 있는가.
3. 데이터·모델·GPU 문제 때문에 뒤늦게 막힐 일이 있는가.
4. 좋아졌다는 주장에 비교 기준과 결과 파일이 있는가.
5. 남은 기간에 맞춰 기능을 빼야 하는가.

PM은 매일 모든 코드를 통제하기보다 범위·기준·의존성·통합을 관리한다. 규칙과 양식은 [복사용 협업 양식](./05-협업양식.md)에 묶었다.
