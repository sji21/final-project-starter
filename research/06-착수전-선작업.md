# 프로젝트 착수 전 선작업

아직 세부 주제·팀별 역할·예산은 확정되지 않았다. 먼저 재사용 가능한 기준과 소량 예제를 준비하고, 큰 구현 결정은 팀 역량·자료 확인에 맞춘다.

## 우선순위와 현재 상태

| 순서 | 선작업 | 끝났다고 판단할 결과물 | 현재 상태 |
| --- | --- | --- | --- |
| 1 | 문제·범위·사용자 흐름 정리 | 대상 사용자, 대표 입력·결과, MVP 경계가 있는 기획안 | 6주 준비안에 초안 작성 |
| 2 | 예제 입력과 기대 결과 | 문서 쌍과 근거가 있는 판정 예시 | 요구사항 6개·테스트 7개 합성 예제 작성 |
| 3 | 판정·평가 기준 | 충족·부분·미기재·모순·확인 필요 정의, 사람이 판정할 기준 | 예제용 초안 작성; 팀 검토 필요 |
| 4 | 데이터 확보 계획 | 실제 이용 가능한 자료, 이용 조건, 정답 작성자, 문서 계열별 분할 계획 | 후보별 확보 여부 확인은 남음 |
| 5 | 에이전트·API 입출력 | 문서·버전·근거·오류·상태 예시와 공통 fixture | JSON 예제 작성; 정식 스키마·API는 미확정 |
| 6 | 베이스라인 평가 준비 | 같은 입력·출력으로 기본 모델을 평가할 실행 경로와 결과 기록 | 실험 양식 작성; 모델 호출·평가 미실행 |
| 7 | 화면 흐름 | 업로드→검토→근거 확인→수정 채택→보고서 화면 초안 | 흐름 제안 완료; 화면 시안 미작성 |
| 8 | 협업·착수 회의 준비 | 역할·PR·업무 카드·실험 기록·주간 데모 규칙 | 협업 규칙·복사용 양식 작성 |
| 9 | RunPod 운영 준비 | GPU 선택 기준·비용 항목·저장·종료·복구 절차 | 운영 원칙 작성; 자원 생성·비용 지출 없음 |

이 표의 “작성”은 로컬 문서·예제를 뜻한다. 팀 저장소에 규칙을 적용하거나 외부 서비스를 설정한 것은 아니다.

## 지금 효과가 큰 다음 작업

### A. 예제로 기획 검증

[문서 검토 예제](./07-문서검토-예제와판정기준.md)를 팀원이 각자 판정한 뒤 의견이 갈리는 부분을 확인한다. 실제 업무에서 중요한 오류인지, 담당자가 제안 결과를 사용할 수 있는지 검토한다. 다른 주제를 고르더라도 이 방식은 재사용할 수 있다.

### B. 실제 자료의 확보 가능성 확인

후보 자료마다 출처, 이용 조건, 형식, 문서 수, 버전, 정답 검토자, 수집 방법을 기록한다. 합성 자료는 구조를 시험하는 데 사용하고 실제 업무 자료의 대체 검증으로 간주하지 않는다. 이 확인이 주제 최종 결정의 핵심이다.

### C. 출력 계약과 평가를 먼저 연결

초기에는 간단한 JSON 입출력으로 요구사항 ID, 연결된 근거, 판정, 사유, 수정 제안을 고정한다. 이 예제로 화면·에이전트·평가 담당자가 같은 형태를 주고받게 한다. 실제 모델이 없어도 모의 응답으로 흐름을 확인할 수 있다.

### D. 작은 베이스라인 실행

주제와 자료가 확인되면 고정된 소량 사례로 기본 모델의 결과를 기록한다. 어떤 오류를 파인튜닝으로 줄일지 정한 뒤 학습 데이터를 확장한다. 베이스라인 실행 전 모델·API 이용 권한과 비용 범위를 확인한다.

## 팀 합의 이후 구체화할 것

- 최종 주제와 실제 문서 유형, 제출 범위.
- 팀원이 유지할 수 있는 백엔드·프런트엔드와 배포 환경.
- 생성형 sLLM의 구체적 학습 태스크·베이스 모델·GPU.
- 데이터 분할·판정 기준을 고정한 뒤의 대량 데이터 제작과 본학습.
- 공유 저장소·외부 협업 도구 설정, 비용이 발생하는 자원 운영.

현재 단계에서는 **예제 → 판정 기준 → 실제 자료 확인 → 작은 베이스라인** 순서가 효율적이다. 전체 제품을 먼저 구현하면 주제나 자료가 바뀔 때 수정할 범위가 커진다.
