# 주제 교체 가이드

## 코드 변경 없이 바꿀 수 있는 범위

기준 문서와 검토 대상 문서를 비교하고 근거·수정안을 만드는 업무입니다. 예를 들어 테스트 명세 검토, CS 응답 품질 확인, 사내 작성 지침에 맞춘 문구 검수 등에 같은 흐름을 사용할 수 있습니다.

외부 DB 조회·메일 발송·일정 예약·이미지 판독처럼 입력과 행동이 달라지면 별도 도구나 단계가 필요합니다. 폴더 이름만 바꾸면 모든 산업의 업무가 완성된다는 뜻은 아닙니다.

## 교체 순서

1. packs/requirements-review를 새 폴더에 복사합니다.
2. 폴더 이름과 manifest.id를 동일한 영문 ID로 바꿉니다.
3. name, description, basis_label, target_label, task, training_task를 새 업무로 작성합니다.
4. 공통 판정 코드 5개는 유지하면서 labels의 화면 이름을 업무에 맞게 바꿉니다.
5. prompts의 extract/review/critic 각각에 해당 업무의 판단 범위를 적습니다.
6. example.json의 pack_id와 문서를 교체합니다. basis/target 역할과 고유 ID를 유지합니다.
7. demo-responses.json의 세 역할 출력을 새 예제에 맞춥니다. 실제 모델 결과와 혼동하지 않게 예제 출처를 남깁니다.
8. 해당 문서 버전과 동일한 hash를 가진 개발용 정답 초안을 만듭니다.
9. 서버를 재시작하고 팩 목록·예제 실행·근거 확인·사람 검토·보고서를 확인합니다.
10. 실제 자료·모델·독립 평가셋을 연결한 후 업무 품질을 검증합니다.

## 교체하지 않는 공통 계약

입력 문서의 ID·version·role·content·complete, 기준의 source, 검토 결과의 criterion_id·verdict·reason·evidence·suggestion, 사람 검토의 revision·action·actor·note를 유지합니다.

원문 인용은 문단 청크 기준입니다. 예를 들어 BASIS 문서의 첫 문단은 BASIS:p1입니다. 빈 줄이 문단을 나누고 긴 문단은 1,200자 단위로 나뉩니다. 원문을 바꾸면 인용과 예제 응답도 다시 맞춰야 합니다.

## 파인튜닝 모델 교체

MODEL_REVIEW에 서버가 노출한 학습 모델 또는 LoRA 별칭을 지정합니다. 원본 모델과 학습 모델은 같은 문서·프롬프트·평가셋으로 비교합니다. 모델을 교체했다고 과제의 학습 요구가 자동 충족되는 것은 아니므로 데이터·학습 설정·체크포인트·학습 전후 결과를 별도로 남깁니다.
